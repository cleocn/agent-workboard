# Test-Issue 触发判断规则

> 统一执行管理规范：[`README.md`](README.md)  
> Management Contract Version：`AWB-WORKITEM-MGMT-v1`  
> Rule Version：`TI-TRIGGER-v1`

## 目的

使用本规则判断是否创建、重新打开或不创建 `test-issue`。发现渠道不构成限制；回归、验收、
代码审查、静态分析、部署或重启验证、日志监控、数据核对以及经确认的用户反馈均可触发判断。

## 判断流程

按顺序执行，任何普通问题未通过前三道门槛时都不创建。

### 1. 预期偏差门槛

确认现有功能、接口或数据契约、部署结果、质量门禁、安全边界或已定义的视觉与交互要求发生
偏差。新功能需求、尚未承诺的能力和主观偏好不属于预期偏差。

### 2. 证据门槛

至少具备一种可保存和复核的证据：

- 稳定或偶发的真实复现，以及时间、请求标识、输入或环境条件；
- 日志、异常、截图、接口响应、数据对比、资源指标或构建产物差异；
- 能证明问题必然发生的静态代码、配置、Schema 或契约证据。

不要求登记时已经确认根因。真实现象成立但根因仍在调查时使用 `待处理`，并在正文明确
“根因待确认”；不要发明 `待验证` 等新状态。

### 3. 处置对象门槛

问题必须能够落到具体组件、类、方法、接口、表、字段、任务、配置、依赖、部署产物或外部
资源，并需要修复、恢复、替换、重新配置或明确延期。只有泛化风险和研究方向时不创建。

### 4. 去重与历史门槛

创建前搜索 `test-issues/`、`test-issues/已解决/` 和历史概要，使用组件、方法、接口、表、字段、
任务名及异常文本作为关键词。

- 已有活动记录：引用并追加本轮复现与影响，不重复创建。
- 已解决问题复发：把原记录改为 `待处理` 并移回根目录。
- 相似现象具有不同组件、根因或独立关闭条件：分别记录，并在正文说明边界。

## 应触发的典型场景

- **确定性静态缺陷**：空值、越权、注入、资源泄漏或确定会违反现有契约的代码路径。
- **跨层契约不一致**：客户端、API、数据库、缓存、消息和数仓之间的字段、类型、可空性、枚举、
  默认值、大小写或时间语义不一致。
- **静默数据错误**：请求表面成功但未保存、未投递、未消费，或报表、计费、曝光、点击、消耗、
  利润等结果缺失或口径错误。
- **部署与恢复错误**：服务器运行旧产物、配置覆盖失败、依赖缺失、重启后不能恢复或源码与运行态
  不一致。
- **可靠性错误**：时序竞争、重复调度、消息丢失或重复、死锁、连接池耗尽、持续重试及可证明的
  偶发超时。
- **安全与隔离错误**：越权、测试开关误开、敏感信息泄露、测试数据越界、误写正式数据或向真实
  外部参与方误发请求或回调。
- **门禁假成功**：关键步骤被跳过、错误被吞掉、只检查进程状态、无有效证据仍判定构建、发布、
  回归或验收成功。
- **客观的视觉与交互缺陷**：在明确设备或输入条件下可复现，并影响信息识别、操作完成、数据
  可信度、无障碍要求或既定视觉验收标准。

## 需要收紧的边界

- **可观测性**：只有缺失日志或监控已导致关键结果无法判定、门禁可能假成功、错误被吞掉或故障
  无法定位到必要程度时才创建。希望增加更多日志不是问题。
- **性能**：只有超过已定义超时或基线、造成失败、积压、重试、资源持续异常或影响验收时才创建；
  “感觉较慢”不是证据。
- **外部资源**：计划停机或一次性网络波动本身不创建。持续阻断回归、配置错误、项目缺少必要的
  超时/恢复处理、恢复后系统不能自愈或同类故障重复发生时创建。
- **偶发问题**：安全、权限、数据污染、计费或报表正确性、真实外部回调、发布与验收假成功等
  高风险问题，一次有效证据即可创建；其他偶发问题需要保留足够的现场证据以便复核。
- **临时兼容方案**：兼容层、配置覆盖或待移除提交本身不创建；只有它已造成具体错误或风险时才
  创建。移除条件继续在 skill、部署文档或提交说明中跟踪。
- **测试覆盖**：缺少自动化用例通常属于测试建设；只有它导致门禁假成功、关键分支错误跳过或
  缺陷反复漏检时才创建。

## 不应触发的场景

- 新功能、产品需求或尚未承诺的能力；
- 没有客观验收标准的视觉偏好或一般优化；
- 单纯重构、清理代码、补文档或补测试计划；
- 尚无证据的猜测、理论风险或调查线索；
- 临时兼容方案或技术债本身；
- 没有系统性原因、未造成残留影响的一次性人工操作失误；
- 已有活动记录覆盖的同一问题。

如果人工操作失误暴露出危险默认值、误导性反馈、缺少必要防护或不可恢复行为，应针对该具体
系统缺陷创建记录，而不是记录“操作失误”。

## 状态选择

- `待处理`：问题和影响已经成立，但修复、根因确认、部署或关闭验收尚未全部完成。
- `暂不处理`：问题已经确认并被明确延期；记录延期原因、当前影响边界和恢复处理条件。
- `已解决`：修复或恢复已完成，关闭证据满足问题范围；同步更新文件名和结果状态并移入
  `test-issues/已解决/`。

只允许以上三种状态。是否已经修复只决定状态和目录，不决定是否保留问题记录。

## 创建后的执行管理

通过创建门槛的新 TI 必须在首次落盘时采用
[`TI / FE / R / WA 统一执行管理模型`](../../../ti-fe-r-wa-execution-management.md)，并从
[`test-issue-template.md`](../assets/test-issue-template.md) 创建。TI 的 `待处理 / 暂不处理 / 已解决`
是问题生命周期状态，不能代替子任务状态。

- 新任务使用 `TI-NNN-T01`、`TI-NNN-T02`……连续编号，至少拆为诊断、处置、验收与收口三个可验证步骤；历史 T00 只能读取，重新补齐时不得持久化；
- 每次状态变化立即更新任务看板、总体进度、当前任务、唯一下一步和状态更新记录；
- `暂不处理` 仍要保留已完成边界、受阻/延期原因、恢复条件和恢复后的第一项任务；
- 所有必需任务和关闭条件取得证据前，不得把 TI 改为 `已解决`；
- 历史 TI 不批量改造，但重新打开或实质扩项时必须先补齐执行管理结构。
